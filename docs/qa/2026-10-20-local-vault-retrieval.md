# 로컬 노트에서 결정 내용을 다시 찾아 작업을 마치는 Comet QA

검증일: 2026-10-20. 작성 주체는 QA를 수행한 AI 어시스턴트다. 합성 여행 준비 작업의 남은 답장 확인을 마무리하는 상황을 네이티브 앱에서 수행했다. 실제 여행·예약·장기 사용 경험을 가장하지 않는다.

## 결론

**로컬 Markdown 연결 → 검색 → 원문 확인 → 수정된 원문 다시 읽기 → 할 일 완료까지 성공했다. 다만 파일을 고친 직후에는 기존 검색 결과가 설명 없이 사라져, 저장된 자료가 없어진 것처럼 느끼기 쉬웠다.**

관찰을 저장 결함과 혼동하지 않는다. 변경된 원문을 검색에서 제외하는 것은 오래된 내용을 보여 주지 않기 위한 보호다. 원문은 남아 있었고 수동 갱신 뒤 새 내용과 함께 다시 열렸다. 이번 보고서는 새로 확정한 기능 버그가 아니라 다음 세 가지 사용성 제안을 다룬다.

1. **높음:** 수정된 원문의 ‘다시 읽기 필요’를 진짜 검색 결과 없음과 구별하고, 검색 화면에서 복구 경로를 제공한다.
2. **중간:** 설정의 검색 시험 결과에서 원문으로 이어지게 하거나, 검색어를 보존하여 실제 검색 화면으로 안내한다.
3. **중간:** 검색 색인과 AI 정리 작업의 상태를 구분하여, 이미 연결된 사용자를 다시 연결하라는 안내로 보내지 않는다.

우선순위는 기능 결함의 심각도가 아니라 이번 여정에서의 개선 검토 순서다. 제안은 구현하지 않았다.

## 검증 대상과 범위

- **실제 조작:** 2026-10-20 **11:36–11:43 UTC**, 클라우드 Linux X11 네이티브 앱. 사용자 Mac이나 웹 미리보기가 아니다.
- **실행 바이너리:** [PR #118](https://github.com/fleetia/comet/pull/118)의 정확한 head `3ae09cf459ba6978ebb3f7d45e877b19df85e5f5`에서 생성된 [Verify desktop CI 산출물](https://github.com/fleetia/comet/actions/runs/39407317084). 기존 검증 바이너리·런타임을 재사용했다. 공식 릴리스 바이너리의 전체 수용 검증으로 표현하지 않는다.
- 기존 합성 작업 프로필을 복사한 별도 QA 프로필을 사용했다. [#119](https://github.com/fleetia/comet/pull/119)의 집중 문맥 수정 검증과는 별개이며, 그 수정의 수용 여부를 이 결과로 판단하지 않는다.
- **로컬 입력:** 합성 Markdown 세 파일만 있는 전용 노트 폴더. `trip-arrival.md`에는 예약 전 늦은 도착 확인 결정, `daily-review.md`에는 준비 회고, `research-focus.md`에는 별도 QA 관찰을 넣었다. 실제 계정·예약·개인 자료·인증정보는 없다.
- 해당 노트 폴더만 연결했다. 포함 경로는 비우고 기본 제외·출력 경로를 유지했다. 전역 자동 정리, Comet 자료 스위치, 해당 Vault의 자동 정리 사용은 모두 **꺼짐**을 확인했다. **‘지금 정리’는 누르지 않았다.**
- 분석 수집도 꺼진 프로필이었다. 이 여정에서는 AI 생성·제공자 연결·계정 인증·실제 외부 자료 전송을 요청하지 않았다.
- 소스상 연결·색인·검색·원문 열기는 로컬 파일과 SQLite를 사용하는 경로다. 이 코드 확인은 **앱 전체의 네트워크 통신이 0이었다는 실측 증거가 아니다.** 네트워크 패킷 계측이나 외부 제공자 동작은 시험하지 않았다.
- 화면을 직접 캡처·검토했지만 **스크린샷 파일을 첨부하거나 업로드하지 않았다.**
- 보고서 기준 main은 `fa66b852e6f6fad48b432023b571e608eaa9f198`이다. 아래 인용한 설정·기록·검색·색인 소스 다섯 파일은 실행한 #118 head와 이 main에서 같은 blob임을 확인했다.

## 기존 보고서와 다른 질문

[기존 기능별 QA](./2026-10-20-v0.18.0-linux-usability.md)는 초기 실행·개별 기능·재시작을, [#117의 작업 여정과 후속 기록](https://github.com/fleetia/comet/pull/117)은 메모·집중·페이지·할 일의 연결과 중단 후 재개를 다룬다.

이번 질문은 **“이전에 로컬 파일에 적어 둔 결정을 찾아 원문을 읽고, 밖에서 수정된 결과를 다시 확인하여 남은 할 일을 마칠 수 있는가?”**다. #117의 빠른 실행·다이어리 메모 검색 관찰과 달리 **Ex-brain에 연결한 로컬 Vault의 원문 검색과 갱신**을 검증한다. 집중 문맥 잔존, 여행 가계부·비용 배분 문제를 다시 세지 않는다.

## 실제 수행한 여정

목표는 `Confirm late arrival response`를 새로 만들지 않고 기존 작업에서 마무리하는 것이었다.

1. **설정 → 일반 → Ex-brain → Vault 연결**에서 세 합성 Markdown이 있는 폴더를 연결했다. 성공 안내는 검색 색인과 정리를 진행 상황에서 확인할 수 있다고 설명했다. 연결 카드에는 ‘검색 자료’가 표시됐지만 상단 진행률은 **0/0**이었다.
2. 설정의 **검색 시험**에서 `reception`을 검색했다. `QA trip arrival decision`과 유용한 발췌문이 나왔다. 제목을 눌러도 원문이 열리지 않았다.
3. 설정의 **정리 기록**으로 이동했다. 첫 화면은 정리 기록이 없으며 AI 연결의 Ex-brain에서 자료를 연결하라고 안내했다. 그래도 **기록·원문 검색**에 `reception`을 입력하자 카드가 나왔다. 카드를 누르면 `trip-arrival.md`의 전체 원문이 열렸다. 합성 자료 표시, 22:00 이후 도착의 사전 확인 결정, 답장 확인 시간, 짐·프로젝트 맥락을 확인했다.
4. 외부에서 원문을 수정한 상황을 만들기 위해 QA 입력 파일에 `Synthetic update: reception confirmed a lockbox handoff. Search marker: amber-lantern.`을 의도적으로 덧붙였다. 이는 **앱의 원문 변경이 아니라 시험 입력 변경**이다.
5. 원문을 닫고 같은 `reception` 검색을 다시 했다. 이 단어가 파일에 그대로 있는데도 **‘일치하는 자료가 없어요.’**만 나왔다. 해당 빈 결과에는 원문 변경·색인 갱신 필요 안내나 갱신 버튼이 없었다.
6. 다이어리의 설정 경로로 돌아가 일반 → Ex-brain → 해당 Vault의 **연결 관리 → 변경 자료 다시 읽기**를 실행했다. 이후 `lockbox` 검색에서 새 내용이 포함된 발췌문을 확인했다.
7. 정리 기록에서 `lockbox`로 검색하고 원문을 열었다. 기존 본문과 추가한 문장이 모두 있었다. **수동 갱신과 복구는 성공했다.**
8. 기존 `Confirm late arrival response` 할 일의 메모에 합성 결정과 원문 파일명을 남겨 저장하고 완료했다. 연결된 준비 봉투의 진행률이 **3/3·100%**가 됐다. 실제 답장·예약·결제는 하지 않았다.

## VAULT-01 — 바뀐 원문이 “자료 없음”으로 보인다

**검토 우선순위: 높음 · 관찰 신뢰도: 높음 · 해석 신뢰도: 높음**

### 관찰과 원인 구분

여정 4–7에서 원문의 기존 검색어를 유지한 채 새 문장을 추가했다. 재검색은 빈 결과였고, 수동으로 다시 읽은 뒤에는 수정된 원문이 정상적으로 검색·열렸다.

[원문 검증과 검색](https://github.com/fleetia/comet/blob/3ae09cf459ba6978ebb3f7d45e877b19df85e5f5/apps/comet/src-tauri/src/organizer/store.rs#L427-L501)은 현재 파일의 내용 해시가 색인된 해시와 다르면 검증을 거절하고, 검증에 성공한 항목만 검색 결과에 넣는다. 반면 [기록 화면의 빈 검색 결과](https://github.com/fleetia/comet/blob/3ae09cf459ba6978ebb3f7d45e877b19df85e5f5/apps/comet/src/widgets/Planner/OrganizerRecords.tsx#L197-L218)는 그 차이를 표시하지 않는다.

따라서 **검색 결과가 사라지는 현상은 확인했지만 파일 삭제·저장 손상·색인 데이터 유실을 입증한 것은 아니다.** 자동 정리를 꺼 둔 이 짧은 시험에서 수동 갱신 전후를 비교했으며, 모든 설정에서 영구히 갱신되지 않는다고 일반화하지 않는다.

### 사용자에게 끼치는 영향

방금 읽은 결정이 검색에서 사라지면 원문을 잃어버렸거나 연결이 끊겼다고 의심하기 쉽다. 현재는 관련 없는 설정 화면을 거쳐 접힌 연결 관리까지 찾아야 한다. 원래 목표였던 답장 확인과 할 일 마무리가 자료 복구 탐색으로 바뀐다.

### 최소 제안과 절충

- 기존 해시 검증을 유지한다. **오래된 본문을 그대로 노출하는 우회는 제안하지 않는다.**
- 현재 연결 범위 안에서 확인 가능한 ‘변경되어 다시 읽기 필요한 자료’와 실제 무일치를 구별한다. 제목·본문을 보여 줄 수 없는 권한 변경·범위 제외·읽기 오류를 같은 상태로 뭉치거나 노출하지 않는다.
- 검색 결과 주변에 해당 Vault의 **‘변경 자료 다시 읽기’** 또는 그 설정으로 가는 직접 경로를 제공한다. 연결을 다시 만들거나 AI 정리를 시작하게 하지 않는다.
- 최소 변경은 갱신 위치를 알리는 안내다. 정확한 제외 사유를 내려 주는 방식은 검색 응답 계약과 오류 처리가 추가로 필요하다. 무조건 매번 전체 폴더를 스캔하면 큰 Vault에서 지연·I/O가 증가하므로 이번 제안의 기본값으로 삼지 않는다.

**후속 확인 기준:** 정상 검색 → 원문 수정 → 새로고침 필요 안내 → 명시적 다시 읽기 → 새 내용 검색·원문 열기가 이어져야 한다. 검색어는 유지하고 오래된 내용은 노출하지 않아야 한다. 삭제·권한 변화·연결 범위 제외·진짜 무일치도 구별해 확인한다. 이는 앞으로의 수용 기준이지 이번에 모두 수행한 테스트가 아니다.

## VAULT-02 — 검색 시험에서 찾은 뒤 같은 검색을 다시 해야 한다

**검토 우선순위: 중간 · 관찰 신뢰도: 높음 · 해석: 검색 표면 사이의 연결 개선**

### 관찰과 사용자 영향

설정에서 제목과 발췌문을 찾았지만 눌러도 열리지 않았다. 정리 기록을 별도로 열고 같은 검색어를 다시 입력한 뒤에야 원문을 읽었다. [설정 검색 결과](https://github.com/fleetia/comet/blob/3ae09cf459ba6978ebb3f7d45e877b19df85e5f5/apps/comet/src/components/OrganizerSettings/OrganizerSettings.tsx#L358-L400)는 제목·발췌문을 출력하는 목록이며 클릭 핸들러가 없다. 반면 [기록 검색 카드](https://github.com/fleetia/comet/blob/3ae09cf459ba6978ebb3f7d45e877b19df85e5f5/apps/comet/src/widgets/Planner/OrganizerRecords.tsx#L197-L218)는 원문 열기를 제공한다.

‘검색 시험’이라는 목적은 맞지만 사용자의 즉각적인 목표는 결과 검증을 넘어 **찾은 결정을 읽는 것**이었다. 원문 접근 기능 자체의 부재나 클릭 이벤트 고장으로 분류하지 않는다.

### 최소 제안과 절충

- 설정 결과에 원문 열기를 제공하거나 **‘정리 기록에서 보기’**로 이동하면서 검색어를 보존한다.
- 설정을 진단용 표면으로 유지하려면 두 번째 방식이 더 작다. 별도 원문 뷰어를 중복 구현하지 않고 기존 경로를 재사용할 수 있다.
- 다만 이동 시 미저장 설정, 활성 사용자·검색 범위 변경, 원문의 최신성 재검증을 보존해야 한다. 이전 검색 결과를 새 사용자나 새 연결 범위로 그대로 넘겨서는 안 된다.

**후속 확인 기준:** 검색 시험에서 찾은 항목을 같은 검색어 재입력 없이 읽을 수 있어야 한다. 뒤로 돌아오면 검색 맥락이 남고, 원문이 이미 바뀌었다면 VAULT-01의 안전한 갱신 경로로 이어져야 한다.

## VAULT-03 — 검색 준비와 정리 진행의 언어가 섞여 있다

**검토 우선순위: 중간 · 관찰 신뢰도: 높음 · 해석 신뢰도: 높음**

### 관찰과 수치의 의미

연결 성공 안내 뒤 **검색은 동작했는데 0/0과 빈 정리 기록**이 함께 보였다. 정리 기록의 빈 안내는 이미 연결한 사용자에게 다시 자료를 연결하라고 권했고, 실제로 접근한 일반 설정이 아닌 ‘AI 연결의 Ex-brain’을 가리켰다.

[설정의 진행 표시](https://github.com/fleetia/comet/blob/3ae09cf459ba6978ebb3f7d45e877b19df85e5f5/apps/comet/src/components/OrganizerSettings/OrganizerSettings.tsx#L267-L298)와 [상태 집계](https://github.com/fleetia/comet/blob/3ae09cf459ba6978ebb3f7d45e877b19df85e5f5/apps/comet/src-tauri/src/organizer/store.rs#L1007-L1033)는 정리 작업과 저장된 정리 기록을 다룬다. **0/0은 검색 색인 문서가 0개이거나 연결이 실패했다는 증거가 아니다.** 자동 정리 없이 원문만 검색하려는 사용자는 성공 여부를 서로 다른 언어에서 해석해야 한다.

### 최소 제안과 절충

- 검색 전용 연결의 성공 안내에서 **‘원문 검색 가능’**과 **‘AI 정리 미실행’**을 분리한다. 정리 작업 수를 색인 완료 수처럼 보이게 하지 않는다.
- [빈 정리 기록 안내](https://github.com/fleetia/comet/blob/3ae09cf459ba6978ebb3f7d45e877b19df85e5f5/apps/comet/src/widgets/Planner/OrganizerRecords.tsx#L219-L226)는 연결 상태에 따라 달리 안내한다. 이미 연결했다면 ‘아직 정리 기록은 없지만 연결한 원문은 위에서 검색할 수 있어요’처럼 기존 검색으로 이어 준다.
- 설정 경로를 안내한다면 현재 실제 위치와 맞춘다. 폴더를 다시 연결하거나 AI 제공자를 설정해야 검색할 수 있다는 인상을 피한다.
- 정확한 문서 수·마지막 색인 시각은 유용할 수 있지만 새 상태 API와 부분 실패 처리가 필요하다. 우선 기존 정보로 가능한 문구 구분부터 검토하고, 근거 없이 ‘색인 완료’라고 표시하지 않는다.

**후속 확인 기준:** 자동 정리 없이도 연결된 원문을 검색할 수 있음을 이해하고, 연결 없음·연결 및 검색 가능·색인 실패·정리 미실행을 혼동하지 않아야 한다. AI 정리를 원하지 않는 사용자에게 불필요한 제공자 연결이나 생성 동작을 권하지 않는다.

## 잘 동작한 부분과 확인하지 않은 범위

### 실제 통과한 범위

- 세 로컬 합성 Markdown 폴더 연결 및 검색.
- 기록 화면에서 발췌문을 넘어 전체 원문 읽기.
- 의도적으로 수정한 파일의 오래된 검색 결과 제외.
- 연결 관리의 수동 다시 읽기 후 새 단어 검색과 기존·추가 본문 확인.
- 읽은 결정과 원문 파일명을 기존 할 일 메모로 남기고 완료하여 준비 봉투 **3/3·100%**로 마무리.
- 최종 노트 폴더에 원본 세 파일이 남았고 생성 결과 폴더는 없었다. 이번 동작에서 앱이 원본을 수정한 정황은 관찰하지 않았다. QA가 의도적으로 덧붙인 문장은 구별한다.

연결과 검색에는 로컬 연결 정보·검색 캐시 저장이 수반된다. [연결·다시 읽기 명령](https://github.com/fleetia/comet/blob/3ae09cf459ba6978ebb3f7d45e877b19df85e5f5/apps/comet/src-tauri/src/organizer/commands.rs#L120-L181), [색인 실행](https://github.com/fleetia/comet/blob/3ae09cf459ba6978ebb3f7d45e877b19df85e5f5/apps/comet/src-tauri/src/organizer/runtime.rs#L183-L225), [검색·원문 열기](https://github.com/fleetia/comet/blob/3ae09cf459ba6978ebb3f7d45e877b19df85e5f5/apps/comet/src-tauri/src/organizer/commands.rs#L283-L335)를 확인했다. 연결 해제를 보안 삭제로 간주하지 않았으며 연결 해제·캐시 삭제 시험은 하지 않았다.

### 미검증 또는 이번 범위에서 제외

- 자동 정리·‘지금 정리’·AI 제공자 호출·요약 품질·정리 결과 생성·되돌리기.
- 실제 사용자 자료, 외부 계정·인증·API, 예약·결제·메시지 전송.
- macOS/Windows 실제 UI, 대용량 Vault, 동시 편집, 장시간 실행, 재시작 후 연결 복원, 삭제·권한 변경·심볼릭 링크의 실기 동작.
- 이 보고서의 제안 구현, 접근성 효과, 정량 성능 비교. 소스 확인을 이 범위의 실기 통과로 세지 않는다.

## 문서 변경과 검증 원칙

문서 한 파일만 추가한다. 앱 코드·디자인시스템·Figma·저장 형식·AGENTS.md·일반 문서 정책을 변경하지 않는다. 실제 UI 변경이 없으므로 디자인 동기화와 수정 전·후 비교는 수행 대상이 아니다.

사용자가 QA 보고서를 PR로 게시하도록 별도로 허용한 범위다. 기존 Fleet 단일 원본 원칙을 다른 설계·계획·일반 문서에 대해 해제하지 않으며, Fleet 원본의 동기화 완료도 주장하지 않는다.

이 문서의 내용·고정 소스 참조·기존 보고서와의 중복·포맷·변경 파일 범위를 확인한다. 문서 작성을 위해 새 앱 빌드나 전체 자동 테스트를 로컬에서 실행한 것은 아니다. 게시 후 CI는 해당 문서 커밋의 결과로 별도 확인하며, CI 통과를 세 UX 제안의 구현이나 실제 플랫폼 전체 수용 검증으로 표현하지 않는다. Draft로 검토를 요청하고 병합·배포하지 않는다.
