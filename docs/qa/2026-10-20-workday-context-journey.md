# 작업 맥락을 남기고 다시 이어가는 Comet 사용 여정 QA

검증일: 2026-10-20. 작성 주체는 QA를 수행한 AI 어시스턴트다. 실제 개인 일정이나 장기 사용 경험을 가장하지 않고, 합성 여행 준비 작업을 네이티브 앱에서 이어서 수행한 결과를 기록한다.

## 한눈에 보는 결론

**메모 작성 → 집중 → 생각 추가 → 중단 → 다음 날짜에 이어가기까지 자료는 이어졌다. 다만 “어디에 꺼냈는지, 어디에 연결했는지, 다음 조작이 어디에 나타났는지”를 화면에서 다시 찾아야 했다.**

이번 제안은 기능 추가보다 기존 기능의 목적지와 상태를 드러내는 데 집중한다.

1. **메모 동작의 목적지 구별:** ‘곁에 꺼내두기’와 ‘바탕화면에 꺼내기’가 서로 다른 결과라는 점을 조작 전에 알리기.
2. **페이지 연결 후 돌아갈 길:** 저장 성공 안내에서 실제 연결된 날짜와 화면으로 이어주기.
3. **할 일 이동의 다음 단계 노출:** 펼쳐진 날짜 선택기가 화면 밖에 생겨 무반응처럼 보이지 않게 하기.

세 항목은 사용성 제안이며 기능 실패로 단정하지 않는다. 별도로 재현한 Linux 집중 타이머의 마우스 선택 문제는 아래의 **확정 기능 버그** 절에 구분했다. 이 PR에서는 어느 제안도 구현하지 않는다.

- 단일 환경의 짧은 정성 관찰이다. 조작 지연을 제품 성능으로 재거나 사용성 개선의 효과를 수치로 입증하지 않았다.

## UX-01 — 같은 “꺼내두기”라도 어디로 가는지 다르다

**검토 우선순위: 중간 · 관찰 신뢰도: 높음 · 해석: 목적지 안내 개선**

### 상황과 실제 동작

작업 중 계속 볼 계획 메모를 원했다. 다이어리 메모 목록에서 봉투 연결 메모의 ‘곁에 꺼내두기’를 누른 뒤 바탕화면을 확인했으나 떠 있는 창은 없었다. 오늘 요약 하단에는 그 메모가 나타났고, 날짜를 다음 날로 바꿔도 고정 메모가 보였다.

반면 별도 바탕화면 메모의 ‘바탕화면에 꺼내기’는 원하는 떠 있는 메모 창을 열었다. [DiaryNotes](https://github.com/fleetia/comet/blob/1351bc3ccc7fdbd36c06774fa050f65ad52344c3/apps/comet/src/widgets/Planner/DiaryNotes.tsx)는 첫 동작을 `DiaryNote.pinned` 변경으로 처리하고, [DiaryDesktopNotes](https://github.com/fleetia/comet/blob/1351bc3ccc7fdbd36c06774fa050f65ad52344c3/apps/comet/src/widgets/Planner/DiaryDesktopNotes.tsx)는 별도 메모 열기 동작을 사용한다. 화면 관찰과 소스가 일치한다.

### 작업에 끼친 영향

성공한 동작을 실패한 것으로 의심하며 바탕화면과 필터를 다시 확인하게 됐다. 메모가 어디로 갔는지 찾는 동안 원래 하려던 작업에서 벗어났다. **바탕화면 메모 기능이 없거나 메모가 유실된 문제는 아니다.**

### 최소 제안과 절충

- 자료형은 유지하고 동작 목적지를 명시한다. 예: 다이어리 고정에는 **‘오늘 화면에 고정’**, 떠 있는 창에는 **‘바탕화면에 표시’**처럼 구별되는 표현을 사용한다.
- 고정 메모가 날짜마다 함께 보이는 계약은 유지한다. ‘오늘’이 특정 하루에만 붙는다고 오해될 수 있다면 ‘오늘 화면에 계속 표시’라는 설명을 보완한다.
- 문구를 구체화하면 기존의 다정하고 가벼운 ‘곁’ 표현은 줄어든다. 짧은 라벨과 보조 설명 중 어느 쪽이 적절한지 검토할 여지가 있다.

**확인 기준:** 처음 보는 메모에서도 누르기 전에 표시될 장소를 구별하고, 조작 직후 그 결과를 찾을 수 있어야 한다. 두 자료형을 자동 변환하거나 복제하는 변경은 이 제안에 포함하지 않는다.

## UX-02 — “연결했어요” 다음에 실제 연결된 화면으로 갈 길이 약하다

**검토 우선순위: 중간 · 관찰 신뢰도: 높음 · 해석: 연결 결과의 재발견 개선**

### 상황과 실제 동작

바탕화면 계획 메모를 오늘 작업과 함께 다시 찾으려고 2026-10-20 페이지에 연결했다. ‘2026-10-20에 연결했어요.’가 나타났고 버튼은 계속 ‘페이지에 연결’이었다. **메모 상세에는 이미 ‘연결 대상: 2026-10-20’이라는 목적지 표시가 있다. 목적지 정보가 전혀 없다는 보고가 아니다.** 오늘을 열었을 때 기본 요약에는 앞서 고정한 봉투 메모가 보였고, 방금 연결한 바탕화면 메모는 ‘한 줄 기록’으로 전환한 뒤에야 본문과 열기·연결 해제를 확인할 수 있었다.

[연결 처리](https://github.com/fleetia/comet/blob/1351bc3ccc7fdbd36c06774fa050f65ad52344c3/apps/comet/src/widgets/Planner/useDiaryWidgetDrop.ts)는 페이지 항목을 만들고 날짜가 담긴 성공 알림을 표시한다. 따라서 **연결 자체가 실패하거나 연결한 메모에 접근할 수 없는 것은 아니다.** 이번 불편은 연결 성공에서 재발견까지의 경로에 있다.

### 작업에 끼친 영향

기본 요약에 보이는 고정 메모와 페이지에 연결된 메모를 비교하며 연결이 제대로 됐는지 다시 확인해야 했다. 다음 날짜로 옮긴 작업을 재개할 때도 요약과 ‘한 줄 기록’ 중 맥락이 있는 곳을 기억해야 했다.

### 최소 제안과 절충

- 성공 알림에 **‘연결한 페이지 보기’**를 제공하고, 실제 연결 항목이 있는 날짜·하위 화면으로 이동시킨다.
- 메모 상세의 **기존 연결 대상 날짜 표시를 유지**하면서, 그 날짜의 실제 항목을 여는 동작을 제공한다. 필요하면 도착할 하위 화면이 ‘한 줄 기록’이라는 짧은 힌트를 보완한다. 복수 연결이 가능하므로 하나의 목적지만 있다고 가정하지 않는다.
- 모든 연결을 기본 요약에 중복 노출하거나 ‘페이지에 연결’ 버튼을 무조건 ‘연결됨’으로 바꾸기보다, **이미 보이는 날짜에서 곧바로 돌아갈 길**을 제공하는 작은 변경을 제안한다.
- 별도의 이동 버튼은 좁은 메모 상세의 정보 밀도를 높인다. 기존 날짜 자체를 탐색 링크로 삼을지, 성공 알림에만 이동 동작을 둘지는 별도 판단이 필요하다.

**확인 기준:** 연결 직후와 메모를 다시 열었을 때, 사용자가 이미 표시된 연결 날짜에서 해당 항목으로 바로 이동할 수 있어야 한다. 같은 원문이 바탕화면과 다이어리에서 동기화되고, 연결 해제가 원문 삭제로 바뀌지 않아야 한다.

## UX-03 — “옮기기”를 눌렀는데 다음 단계가 화면 밖에 생긴다

**검토 우선순위: 중간 · 관찰 신뢰도: 높음 · 해석: 펼쳐진 컨트롤의 가시성 개선**

### 상황과 실제 동작

집중을 중단하면서 할 일 상세와 메모를 펼친 상태에서 ‘옮기기’를 눌렀다. 보이는 영역에 변화가 없어 여러 번 눌렀고, 스크롤한 뒤 상세 아래의 날짜 입력과 ‘이 날짜로 옮기기’를 발견했다. 날짜를 확정하면 실제 이동은 성공했다.

[DiaryPage의 할 일 행](https://github.com/fleetia/comet/blob/1351bc3ccc7fdbd36c06774fa050f65ad52344c3/apps/comet/src/widgets/Planner/DiaryPage.tsx)에서도 ‘옮기기’는 표시 상태를 토글하고, 날짜 폼은 펼쳐진 상세 뒤에 렌더링한다. 관찰한 위치와 일치한다. 모든 창 크기에서 발생한다거나 클릭 이벤트가 유실됐다는 주장은 아니다.

### 작업에 끼친 영향

중단 직전에 다음 행동을 보존하려는 짧은 작업이 “버튼이 작동했는가?” 확인으로 바뀌었다. 토글 버튼을 반복해서 누르면 열고 닫는 상태까지 헷갈릴 수 있다. **이동 실패나 할 일·메모 소실은 관찰하지 않았다.** 원래 날짜의 이동 표식과 다음 날짜의 할 일·메모는 모두 유지됐다.

### 최소 제안과 절충

- 새 날짜 컨트롤이 화면 밖에 있을 때만 보이는 위치로 스크롤하거나, 버튼 가까이에 앵커된 작은 팝오버로 제공한다.
- 펼침 상태를 버튼에 표현하고, 키보드 사용 시 날짜 입력으로 자연스럽게 이어지게 한다.
- 자동 스크롤은 읽던 위치를 바꿀 수 있고, 팝오버는 좁은 창에서 배치·포커스 관리가 필요하다. 우선 현재 인라인 구조를 유지한 채 조건부 노출만 개선하는 편이 변화 범위가 작다.

**확인 기준:** 상세가 접힌 상태·펼쳐진 상태, 긴 메모, 작은 창, 연속 클릭, 취소 후 재열기를 확인한다. 날짜 선택 전에는 이동하지 않고, 확정 뒤 원래 날짜의 이동 흔적과 대상 날짜의 제목·메모가 보존되어야 한다.

## 별도 확정 기능 버그 — 집중 연결의 네이티브 선택창이 닫힘

**분류: Linux 기능 결함 · 영향: 마우스로 할 일 연결을 진행할 수 없음 · 키보드 우회 가능**

1. 접힌 위젯의 집중 타이머 표시를 눌러 말풍선을 연다.
2. ‘이번 집중 연결’을 펼친다.
3. ‘할 일’의 현재 값 ‘연결하지 않음’을 마우스로 누른다.
4. 선택지 목록 대신 말풍선 전체가 닫힌다.

#112의 정확한 CI 바이너리에서 두 번, 공식 v0.18.0에서 한 번 같은 결과를 확인했다. Tab과 ArrowDown/End를 사용하는 키보드 선택은 가능했고, 그 우회로 위 여정의 할 일을 연결했다. 데이터 유실은 관찰하지 않았다.

[WidgetStack](https://github.com/fleetia/comet/blob/1351bc3ccc7fdbd36c06774fa050f65ad52344c3/apps/comet/src/widgets/WidgetDisplay/WidgetStack.tsx)의 창 blur 처리와 [FocusTimerTool](https://github.com/fleetia/comet/blob/1351bc3ccc7fdbd36c06774fa050f65ad52344c3/apps/comet/src/widgets/PlanningTools/FocusTimerTool.tsx)의 네이티브 select 조합이 조사 후보지만, 관찰만으로 최종 원인을 확정하지 않는다. 수정과 회귀 검증은 별도 코드 PR에서 다루며, 본 문서의 세 사용성 제안과 묶어 구현하지 않는다.

## 잘 이어진 부분과 보존해야 할 경험

- 메모를 바탕화면에서 고쳐도 ‘저장됨’ 이후 다이어리에 같은 내용이 나타났다. 집중 중 생각을 별도 창에 추가할 수 있었다.
- 빠른 입력의 종류를 메모에서 할 일로 바꿔도 작성한 제목이 유지됐다.
- 일시 정지한 집중을 끝내도 기록 자체가 없어지지 않았다. ‘기록과 노트’를 스크롤하여 `Review trip preparation`, **1분**, **직접 마침**을 확인했다. 화면에 표시된 구간은 18:48–18:53이었으며, 일시 정지 시간을 제외한다는 요약 설명이 있었다. 표시 구간 전체를 집중 시간으로 계산하거나 UTC 검증 구간과 혼동하지 않는다.
- 다음 날짜로 이동한 할 일에는 중단 시 남긴 메모가 유지됐고, 이전 날짜에는 옮긴 날짜가 남았다. 다시 할 일을 만들 필요가 없었다.

핵심은 기능을 더 붙이는 것보다, 이미 보존되는 작업 맥락에 돌아가는 길을 짧게 하는 것이다.

## 변경 범위와 미검증 항목

이 보고서는 문서 한 파일만 추가한다. 앱 코드·디자인시스템·Figma·저장 형식·전역 문서 정책은 바꾸지 않는다. 사용자에게 별도로 허용받은 QA 보고서 PR 범위이며, 기존 Fleet 단일 원본 원칙을 일반 문서 전체에 대해 해제하는 제안이 아니다.

문서의 내용·참조·차이만 검증한다. 이 PR을 위해 앱 빌드나 전체 자동 테스트를 새로 수행했다고 주장하지 않는다. 제안의 시각적 구현·접근성 효과·macOS/Windows 동작·실제 장기 사용·다중 모니터·인증된 외부 연동은 미검증이다. UI 구현 변경이 없으므로 디자인 동기화나 수정 전·후 비교도 수행 대상이 아니다.
