# 캐릭터 수 1~N 설계안

**상태: 2026-09-16 설계, 2026-09-17 1단계(저장 모델) 구현. 2~4단계 미구현.** 현재 앱은 바탕화면 자리를 `a`/`b` 두 개로 고정하고 각 자리에 캐릭터를 배정한다. 이 문서는 자리 개념을 없애고 활성 캐릭터를 1명부터 여러 명까지 순서 있는 목록으로 다루기 위한 변경 범위, 단계, 아직 결정하지 않은 항목을 정리한다. 구현 전 [상태표](../status.md)와 함께 갱신한다.

## 목표와 비목표

- 사용자는 캐릭터 관리에서 함께 지낼 캐릭터를 추가·제거·순서 변경할 수 있고, 1명·2명·3명 이상이 모두 동작한다.
- 기존 대화 기록·기억·친밀도·단어장·표정 이미지는 보존한다. 친밀도와 메시지 화자는 이미 캐릭터 ID로 저장되어 있으므로 데이터 이전은 자리 표 하나로 한정한다.
- 기존 2인 `.talk` 대본과 `formatVersion 1` 캐릭터팩은 변환 없이 읽을 수 있어야 한다.
- 비목표: 캐릭터마다 별도 말풍선 창, 캐릭터 간 관계 점수, SSP 호환. 이 설계안은 자리 개념 제거까지만 다룬다.

## A/B 가정이 있는 층

| 층 | 현재 | 변경 |
| --- | --- | --- |
| 저장 | `character_slots(slot IN ('a','b'))`, `CharacterCollection.active: [String; 2]` | `active: Vec<String>`(순서 목록). `a`/`b`는 목록 0·1번의 파생값으로 한동안 유지 |
| 대사 데이터 | `SceneLine.persona: "a"\|"b"`, 조합 대사·팩 캐릭터 1~2명, "A와 B가 번갈아" 검증 | 화자를 팩 안 캐릭터 index 또는 `sourceId`로 참조. 교대 검증 폐기, 같은 화자 연속 허용 유지 |
| `.talk` | 화자 `A:`/`B:` 고정(기본 대본 약 267줄), `pair(id, id)` | `cast(id, id, ...)` 선언과 `A`~`Z` 별칭. `pair`는 2인 `cast`의 별칭으로 남김 |

2026-09-16 기준 persona 문자열을 다루는 지점은 Rust `lib.rs` 65곳, `domain.rs` 51곳, `characters.rs` 34곳, `store.rs` 33곳, `desktop.rs` 24곳이며 프론트엔드는 `Balloon.tsx` 23곳이 가장 많다. 단일 커밋으로 바꾸지 않고 아래 단계마다 앱이 동작하는 상태를 유지한다.

## 단계

### 1. 저장 모델 — 2026-09-17 구현

- `character_slots` 대신 `character_roster(position INTEGER PRIMARY KEY, character_id TEXT UNIQUE)`를 만들고 기존 slot 표를 한 번 읽어 0·1번으로 이전한 뒤 slot 표를 삭제한다. 빈 목록으로 시작하면 `builtin-a`·`builtin-b`를 넣는다.
- `CharacterCollection.active`는 `Vec<String>`이다. 기존 코드가 쓰는 `a`/`b` 조회(`active_character`)는 목록 0·1번을 돌려주고, 목록이 1명이면 `b` 조회는 오류를 낸다. `assign("b", id)`는 1명 목록에 두 번째로 덧붙인다.
- 저장 계층 `apply_roster`는 서로 다른 1~8명(`MAX_ROSTER`)을 받는다. 화면·명령(`apply_character_pair`, `assign_character`)은 아직 2명을 유지하므로 실제 앱의 목록은 항상 2명이다.
- 캐릭터 제거 시 목록에 있던 자리를 기본 캐릭터로 대체하는 기존 동작은 2단계에서 1명 화면이 동작할 때까지 유지한다. 2단계에서 "목록에서 빼기, 비면 `builtin-a`"로 바꾼다.
- 겉모습은 바뀌지 않는다. 회귀 테스트: 기존 slot 표의 뒤바뀐 배정 이전과 재초기화 시 재이전 없음, 1명 목록의 `b` 조회·덧붙이기·인원 상한.

### 2. 창과 관리 화면

- `create_boxes`·`sync_boxes`가 목록을 순회해 캐릭터 ID 기반 label(`body-<id>`, `face-<id>`)로 창을 만들고, 목록에서 빠지면 창을 닫는다. 창 위치 저장 키도 캐릭터 ID로 바꾸고 기존 `a`/`b` 위치는 0·1번 캐릭터로 이전한다.
- 말풍선 owner는 캐릭터 ID로 판정한다. 말풍선은 계속 하나만 두고 현재 화자 옆으로 이동한다.
- 캐릭터 관리: 자리 적용 버튼 대신 "함께 지내기 / 내보내기" 토글과 위·아래 순서 버튼. "둘의 자리 바꾸기"는 순서 바꾸기로 대체한다.
- 말풍선 메뉴의 "둘 모두"는 "모두에게"로 바꾸고 `send_message` target을 `all | <id>`로 확장한다.
- 이 단계에서 1명·3명이 화면에 뜬다. 회귀 테스트: 추가·제거 시 창 생성·닫힘, 숨기기·보이기가 전 캐릭터에 적용되는지.

### 3. 대사 데이터와 LLM

- `SceneLine.persona`를 화자 참조로 바꾼다. 팩 안에서는 `speaker: <index>`(0부터), 로컬 저장은 캐릭터 ID. 캐릭터팩은 `formatVersion 2`로 올리고 v1은 `a→0`, `b→1`로 읽어 변환한다. v2 팩의 캐릭터 수 상한은 8명으로 시작한다.
- 조합 대사(`character_dialogues`)의 `members`는 이미 정렬된 ID 목록 키이므로 인원 상한만 푼다. 혼합 조합 규칙(각 캐릭터의 단독 대사 사용)은 그대로다.
- LLM 응답 schema의 `persona` enum을 활성 캐릭터 이름(또는 index)으로 만들고, 시스템 프롬프트의 "a와 b가 번갈아"를 "활성 캐릭터가 각 1문장, 총 N줄 이하"로 바꾼다. 1명일 때는 아래 결정 대기 항목에 따른다.
- 개인 단어장의 화자도 캐릭터 ID로 바꾸되, 기존 항목의 `a`/`b`는 저장 시점 0·1번 캐릭터로 고정 이전한다.
- 내보내기: 선택 캐릭터 1~N명. 회귀 테스트: v1 팩 왕복, 화자 index 재배치, 3인 장면 재생 순서.

### 4. `.talk` 대본

- 파일 머리에 `cast: A=<id>, B=<id>, C=<id>` 또는 `import ... for cast(id, id, id)`를 허용하고 화자 별칭을 `A`~`Z`로 확장한다. 별칭이 없는 파일은 활성 목록 순서로 `A`, `B`, `C`…에 대응한다.
- 기본 대본 130개 장면은 2인 전제이므로 손대지 않고, 활성 캐릭터가 1명이면 `B` 대사가 있는 장면은 후보에서 제외한다. 3명 이상이면 0·1번 캐릭터가 `A`·`B`를 맡는다.
- `pair(id, id)`는 `cast`의 2인 별칭으로 유지한다. CLI `talk check`는 캐스트 인원과 화자 별칭 범위를 함께 검사한다.

## 위험과 순서 조건

- 3단계에서 팩 형식이 바뀌면 "1~2명 팩" 문서 약속이 깨진다. 변환기는 두되 문서와 예제 팩을 함께 갱신한다.
- 1인 모드는 현재 제품 계약인 "둘이 주고받는 수다"와 충돌한다. 기본 대본 대부분이 2인 대화이므로 결정 대기 첫 항목을 먼저 정한다.
- 예상 규모는 3~4일이다. 표정 이미지·투명 창·말풍선 이미지 변경을 먼저 커밋한 뒤 별도 브랜치에서 시작한다.
- 각 단계는 `cargo test`, 프론트엔드 테스트, `pnpm check`와 함께 2인 구성의 기존 동작(인사·자동 수다·키워드 재생·숨기기·재시작 보존)이 그대로인지 확인한 뒤 다음 단계로 넘어간다.
