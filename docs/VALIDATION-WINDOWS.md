# Windows 실제 검증

2026-09-26 Windows에서 수행한 검증 기록이다. 코드 검사, 실제 데스크톱 조작, 모델의 의미 품질과 공식 업데이트를 구분한다. 전체 인수는 진행 중이며 아래 미완료 항목은 자동 테스트 통과로 대체하지 않는다.

## 환경과 데이터

- Windows 11 Home x64, Ryzen 7 5800X3D, RAM 64GB, RTX 3080, 모니터 2대.
- 별도 앱 식별자 `space.starlight.comet.windows-qa`와 합성 데이터 사용.
- Node.js 24.19.0, pnpm 11.27.0, Rust release 빌드.
- 일반 Comet 프로필과 사용자 모델은 검증 데이터로 사용하지 않았다.

## 코드 검사

프런트엔드 검사·production build와 Vitest 47개 파일·283개 테스트를 통과했다. Cargo 컴파일과 겹친 기본 병렬 실행에서 2개 테스트가 시간 제한을 넘겼고, 작업자 2개로 제한한 전체 재실행은 모두 통과했다. Windows release Rust 라이브러리 테스트는 483개 통과, 기존 3개 제외, 실패 0개였다.

Windows의 전체 target strict Clippy에서 발견한 조건부 import와 기존 lint 오류를 정리했다. 실행 경로의 잠금 수명과 반환값을 유지했다. 캐릭터 명령·얼굴 위치 수정 단계에서 `cargo clippy --locked --release --all-targets -- -D warnings`와 release 라이브러리 테스트 484개를 통과했다. 기존 3개는 제외했고 실패는 0개다. 실제 모델을 사용하는 검사는 별도로 기록한다.

로컬 추론기의 Windows DLL 탐색 경로 수정까지 포함한 최종 소스에서는 `cargo fmt --check`, release 라이브러리 테스트 485개 통과·3개 제외, 전체 target strict Clippy를 다시 통과했다. 아래 설치본은 이 소스로 다시 빌드했다.

## 캐릭터 구성 적용 중 정지

기존 별꼬리 한 명이 있는 QA 앱에서 `examples/character-packs/nadir-and-star-tail.comet-character.json`을 가져왔다. 미리보기와 설치는 성공했으나 `가져온 친구와 함께 지내기`를 누르면 `처리 중…`에서 멈추고 새 본체 창이 나타나지 않았다.

읽기 전용 DB 조회에서 기존 별꼬리와 추가한 두 캐릭터가 저장되고 `character_roster`에도 세 ID가 반영된 것을 확인했다. `PRAGMA integrity_check`는 `ok`였다. 합성 DB를 백업한 뒤 멈춘 QA 프로세스만 종료했다.

원인은 `apply_character_roster`의 동기 Tauri 명령에서 `publish` → `desktop::sync_boxes` → `WebviewWindowBuilder::build`를 호출하는 경로다. [Tauri의 Windows 제한](https://docs.rs/tauri/latest/x86_64-pc-windows-msvc/tauri/webview/struct.WebviewWindowBuilder.html)은 동기 command와 event handler에서 창을 만들면 교착될 수 있다고 명시한다. 같은 창 생성 경로에 도달하는 캐릭터 변경 명령 7개를 비동기로 전환했다. DB transaction과 취소·revision 처리 순서는 유지한다.

수정한 NSIS 설치 파일의 SHA-256은 `f6f902f4784498f09883d89c2528ac18837bf53e0196152577617f1d95252866`이다. QA 앱에 덮어 설치한 뒤 16:43 KST에 실행해 저장된 세 캐릭터가 모두 복구되는 것을 확인했다. 실행 중 텍스트 캐릭터를 구성에서 빼고 다시 넣으면 3→2→3명이 정상 반영되고 새 본체 창이 생성됐다. 이미지 캐릭터도 같은 왕복에서 본체와 표정 창이 함께 제거·재생성됐다. 순서 변경을 두 번 적용해 원래 순서로 돌리는 동작도 확인했다.

## 분리 얼굴의 모니터 복원

얼굴 창의 위치는 본체와 별도로 저장하지만, 재시작 때 저장 좌표를 본체 모니터 영역으로 제한하는 결함을 코드에서 확인했다. 저장 좌표가 속한 모니터를 먼저 선택하는 기존 본체 규칙을 얼굴에도 적용했다. 해당 모니터가 없으면 본체의 현재 모니터, 기본 모니터 순으로 복원한다. 음수 좌표의 다른 모니터 선택과 모니터 분리 때의 fallback 진입을 회귀 검사했다.

이 PC의 두 모니터는 각각 2560×1440이며 배치는 `(-2560, 0)`과 `(0, 0)`이다. 자동 조작 도구는 창 범위를 벗어나는 드래그를 거절했고 창 내부의 짧은 드래그도 실제 위치를 바꾸지 못했다. 따라서 얼굴의 실제 모니터 간 이동·복원과 혼합 DPI 검증은 사용자 조작을 기다린다.

## 기기·음악 위젯 준비

QA 설정에서 기기 소식과 음악 정보 위젯을 함께 설치하고 각각 연결을 활성화했다. 기기 창은 배터리가 없는 이 PC에서 `조회 가능한 배터리가 없어요`와 조회 성공 시각을 표시했다. 실제 절전·복귀는 아직 수행하지 않았다.

음악 제공자를 `시스템 미디어 · Windows`로 설정하고 실제 위젯 창을 열었다. 실행 중인 미디어 세션이 없는 상태에서 앱이 닫혀 있다는 안내와 비활성 재생 제어가 표시됐다. 로그인된 Spotify의 재생·아트워크·재연결 검증은 아직 수행하지 않았다.

## QA 데이터 이전 경계

일반 앱과 다른 식별자의 QA 앱도 이전 `space.starlight.nanika-box` 폴더를 찾는 소스 경로를 확인했다. QA DB가 이미 있어도 이전 폴더의 대본·스토리·모델을 이동할 수 있어, 이전 작업을 일반 앱 데이터 폴더 `space.starlight.comet`에만 허용했다. QA DB와 이전 폴더의 합성 DB·모델·대본이 모두 남는 회귀 테스트를 추가했다. migration 테스트 7개와 수정 후 전체 target strict Clippy를 통과했다.

공식 v0.5.0의 합성 데이터는 QA 앱이 종료된 뒤 처음 생성했다. 수정 전 QA 앱을 다시 실행하지 않았으며, 새 QA 실행 전 이전 프로필의 33개 파일 해시를 저장했다. 설치본으로 실행한 뒤의 보존 확인은 별도로 기록한다.

## 로컬 모델 준비

현재 카탈로그가 고정한 URL에서 Qwen3.8 2B·4B·9B, Gemma 4 E4B·12B, Ministral 3 8B의 GGUF 6개를 내려받았다. 각 파일의 바이트 수와 SHA-256이 카탈로그 값과 일치했다. 다운로드에는 별도 QA 스크립트를 사용했으며 앱 다운로드 화면을 통한 검증은 아니다. 앱에 동봉한 sidecar와 같은 실행 옵션으로 로딩·JSON 응답을 아래와 같이 확인했다.

Windows 설치본에서 `llama-server.exe`가 backend DLL을 찾지 못하던 원인을 확인하고, 앱 소유 프로세스의 작업 디렉터리를 동봉 `runtime/`으로 지정했다. 수정 소스로 만든 NSIS 설치 파일의 SHA-256은 `8edad68cde74a3ff80227a8b224eec66af8363dd71ebf092fc9a2f2d06ab5b83`이다. 별도 QA 앱에 설치해 정상 실행했고, 설정에서 저장 전 직접 지정한 Qwen3.8 2B GGUF로 `테스트하기`를 눌러 5.1초 응답과 테스트 뒤 sidecar 종료를 확인했다. 모델 선택은 `변경 취소`로 기존 Qwen3.5 4B 설정으로 되돌렸다.

동봉 sidecar와 앱 옵션을 사용하는 별도 QA harness에서 여섯 모델에 인사 cold/warm과 합성 의미 질문 4개씩 총 36응답을 기록했다. 아래 시간은 이 PC의 단일 실행이며 cold에는 모델 로딩을 포함한다. 원문 결과는 ignored `work/windows-qa-20260926/models/inference-results-app-args.ndjson`에 있다.

## Windows NLP 설치와 재시작

별도 QA 앱 설정에서 공식 Kiwi 88.0 MB를 내려받아 활성화했다. 화면에 `기본 검색 · 한국어 분석`과 `검색 준비 완료`가 표시됐고 정상 종료·재시작 뒤에도 유지됐다. 설치 영수증과 9개 파일의 크기·SHA-256이 manifest와 일치했다. 설치된 `comet-nlp.exe`를 별도 실행한 합성 한국어 JSONL 질의에서 ready 응답, 오류 없는 토큰 15개와 올바른 UTF-8 바이트 경계, 정상 종료를 확인했다. 앱 정상 종료 뒤 소유 추론·NLP 자식 프로세스는 남지 않았다.

QA DB는 SQLite backup API로 Kiwi 설치 전·후 백업을 만들고 읽기 전용으로 확인했다. 설치 전 메시지 46건의 `id·role·data` 해시가 설치 후 첫 46건과 같고, 자동 대화 3건이 추가돼 총 49건이 됐다. 이 시점의 기억은 0건, 두 백업의 무결성은 `ok`다. 실제 기억 검색·인덱싱, 다운로드 취소·손상 복구, 8GB·4논리 CPU·GPU 없는 기준 기기의 자원 측정은 이 단계에서 확인하지 않았다. E5는 URL·출시 threshold가 비어 있어 의미 검색 설치·사용을 제공하지 않는다. 기존 macOS 평가의 held-out Recall@5 66.67%·무관 질문 오탐 10%는 90%·5% 목표에 미달하며 Windows 품질 결과가 아니다.

## 키 없는 로컬 OpenAI 호환 API

사용자 결정에 따라 API 모드의 정확한 `localhost`·`127.0.0.1`·`[::1]` 주소에 한해 키 없는 연결을 허용했다. 직접 대화·허용된 자동 생성·연결 테스트가 같은 준비 조건을 쓰고, 원격 API는 요청 직전에도 키를 요구한다. 설정 저장과 실제 요청의 URL 검사도 같은 경로를 사용한다. 프런트엔드 47개 파일·285개 테스트, release Rust 라이브러리 직렬 실행 489개 통과·3개 제외, 전체 target strict Clippy, 위키 타입 검사·정적 빌드를 통과했다. Rust 병렬 실행에서는 이 변경과 무관한 음악 브리지 테스트 한 건이 Windows 연결 재설정으로 실패했으나 해당 단건과 직렬 전체 재실행은 통과했다.

키 없는 API 경로를 화면에서 확인한 빌드의 NSIS SHA-256은 `54bf80ac8db25b5ef0dc2789c534a87aa5bb0284460ebb791395408a30774264`다. 이후 로컬 API와 앱 소유 sidecar의 HTTP 요청에 시스템 프록시를 적용하지 않도록 보완했다. 가짜 프록시를 지정한 로컬 무인증 연결 회귀, `cargo fmt --check`와 release strict Clippy를 통과했다. 이 최종 소스의 NSIS SHA-256은 `032652a90dcfdda9baebc3b492a1e613feb2cc5e2185beb8a83aeb0b6f02b123`이다.

검증 중 일반 Comet 앱이 실행돼 설치 프로그램의 동명이인 프로세스 종료를 피하고자, 종료된 별도 QA 설치 폴더의 `comet.exe`만 새 release 실행 파일로 교체했다. 최종 빌드와 QA 설치 폴더의 실행 파일 SHA-256은 `3965955ca1c111bc8c8a7e32d60a721a2fa404aa3865211caefa598973eff177`로 같다. QA 앱은 정상 실행됐고 일반 앱은 계속 실행됐다. 이번 NSIS 자체의 재설치 경로는 확인하지 않았다.

QA 설정에서 `http://127.0.0.1:8765/v1`과 합성 모델명을 키 없이 입력하자 `연결 테스트`가 활성화되고 성공했다. API 모드를 저장해 합성 문장을 나디르에게 보내자 `지난 대화`에 사용자 입력과 `QA 로컬 API 응답이야.`가 함께 표시됐다. 이 기기에만 열린 합성 OpenAI 호환 서버는 두 요청에서 Authorization 헤더가 없음을 기록했다. 테스트 뒤 QA 설정을 원래 로컬 모델 방식으로 복원하고 앱과 합성 서버를 정상 종료했다. 실제 Ollama·LM Studio의 모델 응답과 원격 제공자의 인증 동작은 이번 화면 검증 범위가 아니다.

이 프록시 보완 전 QA 종료 후 DB를 읽기 전용으로 검사했다. 실행 전 백업의 기존 메시지 49건과 실행 후 첫 49건의 `id·role·data` 해시가 같고, 자동 장면 3건과 완료된 합성 입력·응답 각 1건이 추가돼 총 54건이다. 무결성 검사는 `ok`였으며 Kiwi 활성 설정과 복원한 로컬 모델 연결 방식도 유지됐다. 이 54건 결과는 아래 최종 실행 파일의 기억 분석·재시작 이후 DB 상태를 뜻하지 않는다.

프록시 보완을 포함한 최종 실행 파일에서 합성 loopback 서버로 키 없는 `연결 테스트`와 직접 대화를 다시 확인했다. 보류 중이던 원문 분석을 실행하고 QA 앱을 재시작한 뒤, 합성 `user_fact` 기억 한 건(`b83ecdc8-83de-41e6-83c5-aa9f6e00014f`)과 Kiwi 색인을 확인했다. 다음 대화 요청의 프롬프트에는 이 기억 ID가 포함됐다. ignored `work/windows-qa-20260926/keyless-memory-qa-log.ndjson`의 연결 1건·대화 3건·분석 1건 모두 `authorization: false`였다. 응답과 추출한 사실은 QA mock의 고정값이므로 실제 모델의 의미 품질을 증명하지 않는다.

이 합성 API·기억 QA에서는 모델 연결 방식과 선택을 원래 로컬 Qwen3.5 4B로 다시 저장했다. 자동 설정 화면에서 `localIdleEnabled`와 `apiIdleEnabled`를 모두 `false`로 저장하고 QA 앱을 정상 종료했다. QA 프로필에서 진행 중이던 Gemma 다운로드의 `.part` 파일 3,255,917,307 bytes는 삭제하지 않고 보존했다. 실제 Ollama·LM Studio 서버 연결·응답, 원격 제공자의 인증 동작과 이번 NSIS 자체의 재설치는 아직 검증하지 않았다.

이 합성 API·기억 QA를 종료한 뒤, 합성 기억을 만들기 전의 QA 프로필 전체 백업과 당시 DB를 읽기 전용으로 대조했다. 백업 메시지 54건과 당시 첫 54건의 `(id, role, data)`가 순서까지 같고 당시 총 74건이다. 앞선 71건 점검 뒤 재시작·자동 대화 3건이 더해졌다. 기억은 백업 0건에서 합성 `user_fact` 1건으로 늘었으며, 그 ID `b83ecdc8-83de-41e6-83c5-aa9f6e00014f`가 `memory_tokens`에도 있다. `PRAGMA integrity_check`는 `ok`다. 백업·당시 `settings` JSON은 완전히 같고 로컬 Qwen3.5 4B, `autonomousEnabled: true`, 두 idle flag `false`, `idleMinutes: 2`, API URL·모델·token parameter가 유지됐다. `nlp/memory-search.json`도 완전히 같으며 `{kiwiEnabled: true, semanticEnabled: false}`다. 당시 종료 점검에서는 소유 mock PID 36880을 멈춘 뒤 QA 앱·소유 자식·mock 프로세스가 남지 않았고 일반 Comet PID 39792만 실행 중이었다. 이 보존 확인은 아래 실제 GGUF API 시험 전의 합성 QA 프로필에 한정한다.

## 동봉 GGUF 서버의 키 없는 로컬 API 시험

설치본의 `llama-server.exe`와 동봉 `runtime/`을 사용해 SHA-256 `4aa0fb13c431514262f259d420ecc95a8714df58ac2a2384514e20b93983f0ff`로 검증한 Qwen3.8 2B GGUF를 별도 소유 서버(PID 39332)로 숨김 실행했다. `127.0.0.1:18765`의 `/health`는 200을 반환했고, 서버에 `LLAMA_API_KEY` 환경변수나 `--api-key` 옵션을 주지 않았다. 최신 QA 실행 파일의 설정 화면에 `http://127.0.0.1:18765/v1`, 모델 `local`을 키 없이 입력했다. 기존 `max_completion_tokens` 선택으로 처음 누른 `연결 테스트`는 필수 JSON이 빠졌다는 오류를 냈다. token parameter를 `max_tokens`로 바꿔 재시도하자 연결에 성공했다. API 모드를 저장하고 나디르에게 `QA 실제 모델 시험이야. 오늘 기분을 한국어 한 문장으로 말해줘.`를 보내자 `지난 대화`에 실제 모델 응답 `QA 시험을 준비하는 날, 기분이 평온합니다.`가 표시됐다.

이 한 건은 동봉 llama.cpp 서버가 키 없는 OpenAI 호환 API로 응답한 Windows 실기다. 실제 Ollama·LM Studio 연결이나 넓은 의미 품질, `max_completion_tokens` 호환성을 증명하지 않는다.

시험 뒤 QA 앱을 정상 종료하고 소유 `llama-server.exe` PID 39332를 멈췄다. 이때 일반 Comet PID 39792만 남았다. 합성 기억 생성 전 백업과 최종 QA DB를 읽기 전용으로 다시 대조하니 메시지는 54건에서 82건으로 늘었고, 첫 54건의 `(id, role, data)`와 순서는 그대로였다. 합성 기억 한 건과 같은 ID의 Kiwi 색인을 유지했고 `PRAGMA integrity_check`는 `ok`였다. 백업·최종 `settings` JSON과 `nlp/memory-search.json`은 각각 완전히 같아 로컬 모델 방식·API 값·자동 설정·Kiwi 설정이 복원됐다. Gemma 다운로드 `.part` 파일도 3,255,917,307 bytes로 남아 있다. 위 74건은 이 실제 GGUF API 시험 전의 중간 점검값이다.

## 공식 이전 버전과 업데이트 조건

공개된 [v0.5.0](https://github.com/fleetia/comet/releases/tag/v0.5.0)의 Windows 설치 파일, updater 서명 파일과 `latest.json`을 내려받았다. 설치 파일 SHA-256은 `f23f9adb2a8c67a82f3396923f55675d6137e4eaa97c4ef9f82b43f65b021b73`이다. NSIS 설치가 종료 코드 0으로 끝났고, 17:25 KST의 첫 실행에서 위젯 온보딩과 나디르·텍스트 별꼬리 본체를 확인했다. 이 버전은 이전 식별자 `space.starlight.nanika-box`에 새 합성 데이터를 만들었다.

공식 v0.5.0 설치 과정에서 같은 실행 파일 이름의 QA 앱도 종료됐다. 그 전에 시작한 1시간 스토리 계측은 인수 근거로 쓰지 않는다. v0.6.0은 Windows 아트워크 코드의 `Send` 오류로 빌드에 실패한 초안이다. 고정된 태그를 옮기지 않고 새 버전을 배포해야 하며, 현재 버전 PR은 [v0.7.0 #12](https://github.com/fleetia/comet/pull/12)다. 더 높은 signed 버전이 공개된 후에 공식 업데이트 설치·재시작과 데이터 이전을 검증할 수 있다.
