# Windows 실제 검증

2026-09-26 Windows에서 수행한 검증 기록이다. 코드 검사, 실제 데스크톱 조작, 모델의 의미 품질과 공식 업데이트를 구분한다. 전체 인수는 진행 중이며 아래 미완료 항목은 자동 테스트 통과로 대체하지 않는다.

## 환경과 데이터

- Windows 11 Home x64, Ryzen 7 5800X3D, RAM 64GB, RTX 3080, 모니터 2대.
- 별도 앱 식별자 `space.starlight.comet.windows-qa`와 합성 데이터 사용.
- Node.js 24.19.0, pnpm 11.27.0, Rust release 빌드.
- 일반 Comet 프로필과 사용자 모델은 검증 데이터로 사용하지 않았다.

## 코드 검사

프런트엔드 검사·production build와 Vitest 47개 파일·283개 테스트를 통과했다. Cargo 컴파일과 겹친 기본 병렬 실행에서 2개 테스트가 시간 제한을 넘겼고, 작업자 2개로 제한한 전체 재실행은 모두 통과했다. Windows release Rust 라이브러리 테스트는 483개 통과, 기존 3개 제외, 실패 0개였다.

Windows의 전체 target strict Clippy에서 발견한 조건부 import와 기존 lint 오류를 정리했다. 실행 경로의 잠금 수명과 반환값을 유지했다. 캐릭터 명령·얼굴 위치 수정 후 `cargo clippy --locked --release --all-targets -- -D warnings`와 release 라이브러리 테스트 484개를 통과했다. 기존 3개는 제외했고 실패는 0개다. 실제 모델을 사용하는 검사는 별도로 기록한다.

## 캐릭터 구성 적용 중 정지

기존 별꼬리 한 명이 있는 QA 앱에서 `examples/character-packs/nadir-and-star-tail.comet-character.json`을 가져왔다. 미리보기와 설치는 성공했으나 `가져온 친구와 함께 지내기`를 누르면 `처리 중…`에서 멈추고 새 본체 창이 나타나지 않았다.

읽기 전용 DB 조회에서 기존 별꼬리와 추가한 두 캐릭터가 저장되고 `character_roster`에도 세 ID가 반영된 것을 확인했다. `PRAGMA integrity_check`는 `ok`였다. 합성 DB를 백업한 뒤 멈춘 QA 프로세스만 종료했다.

원인은 `apply_character_roster`의 동기 Tauri 명령에서 `publish` → `desktop::sync_boxes` → `WebviewWindowBuilder::build`를 호출하는 경로다. [Tauri의 Windows 제한](https://docs.rs/tauri/latest/x86_64-pc-windows-msvc/tauri/webview/struct.WebviewWindowBuilder.html)은 동기 command와 event handler에서 창을 만들면 교착될 수 있다고 명시한다. 같은 창 생성 경로에 도달하는 캐릭터 변경 명령 7개를 비동기로 전환했다. DB transaction과 취소·revision 처리 순서는 유지한다.

수정한 NSIS 설치 파일의 SHA-256은 `f6f902f4784498f09883d89c2528ac18837bf53e0196152577617f1d95252866`이다. QA 앱에 덮어 설치한 뒤 16:43 KST에 실행해 저장된 세 캐릭터가 모두 복구되는 것을 확인했다. 실행 중 텍스트 캐릭터를 구성에서 빼고 다시 넣으면 3→2→3명이 정상 반영되고 새 본체 창이 생성됐다. 이미지 캐릭터도 같은 왕복에서 본체와 표정 창이 함께 제거·재생성됐다. 순서 변경을 두 번 적용해 원래 순서로 돌리는 동작도 확인했다.

## 분리 얼굴의 모니터 복원

얼굴 창의 위치는 본체와 별도로 저장하지만, 재시작 때 저장 좌표를 본체 모니터 영역으로 제한하는 결함을 코드에서 확인했다. 저장 좌표가 속한 모니터를 먼저 선택하는 기존 본체 규칙을 얼굴에도 적용했다. 해당 모니터가 없으면 본체의 현재 모니터, 기본 모니터 순으로 복원한다. 음수 좌표의 다른 모니터 선택과 모니터 분리 때의 fallback 진입을 회귀 검사했다.

이 PC의 두 모니터는 각각 2560×1440이며 배치는 `(-2560, 0)`과 `(0, 0)`이다. 자동 조작 도구는 창 범위를 벗어나는 드래그를 거절했고 창 내부의 짧은 드래그도 실제 위치를 바꾸지 못했다. 따라서 실제 모니터 간 이동과 혼합 DPI 검증은 사용자 조작을 기다린다. 이 수정의 새 설치본 실행도 별도로 확인해야 한다.

## 기기·음악 위젯 준비

QA 설정에서 기기 소식과 음악 정보 위젯을 함께 설치하고 각각 연결을 활성화했다. 기기 창은 배터리가 없는 이 PC에서 `조회 가능한 배터리가 없어요`와 조회 성공 시각을 표시했다. 실제 절전·복귀는 아직 수행하지 않았다.

음악 제공자를 `시스템 미디어 · Windows`로 설정하고 실제 위젯 창을 열었다. 실행 중인 미디어 세션이 없는 상태에서 앱이 닫혀 있다는 안내와 비활성 재생 제어가 표시됐다. 로그인된 Spotify의 재생·아트워크·재연결 검증은 아직 수행하지 않았다.

## QA 데이터 이전 경계

일반 앱과 다른 식별자의 QA 앱도 이전 `space.starlight.nanika-box` 폴더를 찾는 소스 경로를 확인했다. QA DB가 이미 있어도 이전 폴더의 대본·스토리·모델을 이동할 수 있어, 이전 작업을 일반 앱 데이터 폴더 `space.starlight.comet`에만 허용했다. QA DB와 이전 폴더의 합성 DB·모델·대본이 모두 남는 회귀 테스트를 추가했다. migration 테스트 7개와 수정 후 전체 target strict Clippy를 통과했다.

공식 v0.5.0의 합성 데이터는 QA 앱이 종료된 뒤 처음 생성했다. 수정 전 QA 앱을 다시 실행하지 않았으며, 새 QA 실행 전 이전 프로필의 33개 파일 해시를 저장했다. 설치본으로 실행한 뒤의 보존 확인은 별도로 기록한다.

## 로컬 모델 준비

현재 카탈로그가 고정한 URL에서 Qwen3.8 2B·4B·9B, Gemma 4 E4B·12B, Ministral 3 8B의 GGUF 6개를 내려받았다. 각 파일의 바이트 수와 SHA-256이 카탈로그 값과 일치했다. 다운로드에는 별도 QA 스크립트를 사용했으며 앱 다운로드 화면을 통한 검증은 아니다. 앱에 동봉한 sidecar와 같은 실행 옵션으로 로딩·JSON 응답·한국어 의미 품질을 이어서 확인한다.

## 공식 이전 버전과 업데이트 조건

공개된 [v0.5.0](https://github.com/fleetia/comet/releases/tag/v0.5.0)의 Windows 설치 파일, updater 서명 파일과 `latest.json`을 내려받았다. 설치 파일 SHA-256은 `f23f9adb2a8c67a82f3396923f55675d6137e4eaa97c4ef9f82b43f65b021b73`이다. NSIS 설치가 종료 코드 0으로 끝났고, 17:25 KST의 첫 실행에서 위젯 온보딩과 나디르·텍스트 별꼬리 본체를 확인했다. 이 버전은 이전 식별자 `space.starlight.nanika-box`에 새 합성 데이터를 만들었다.

공식 v0.5.0 설치 과정에서 같은 실행 파일 이름의 QA 앱도 종료됐다. 그 전에 시작한 1시간 스토리 계측은 인수 근거로 쓰지 않는다. v0.6.0은 Windows 아트워크 코드의 `Send` 오류로 빌드에 실패한 초안이다. 고정된 태그를 옮기지 않고 새 버전을 배포해야 하며, 현재 버전 PR은 [v0.7.0 #12](https://github.com/fleetia/comet/pull/12)다. 더 높은 signed 버전이 공개된 후에 공식 업데이트 설치·재시작과 데이터 이전을 검증할 수 있다.
