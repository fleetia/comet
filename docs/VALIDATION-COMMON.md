# 공통 데스크톱 인수 기록

2026-09-27의 공통 검증 기록이다. 제품 계약은 [바탕화면](product/desktop.md)·[대화](product/conversation.md)·[토이](product/toys.md)를 따른다. 아래의 소스·자동 검사·네이티브 관찰·모델 의미 품질을 구분하며, 전체 플랫폼 인수는 아직 완료하지 않았다. 이전 Windows 결과는 [Windows 기록](VALIDATION-WINDOWS.md)에 보존한다.

## 이번 소스 수정

- 비눗방울 충돌과 클릭은 같은 `pop_bubble` 경계에서 한 번만 결과를 확정한다. 기존에는 충돌 후 다음 물리 tick에서 제거되기 전 클릭이 들어오면 같은 물체의 결과를 다시 만들 수 있었다. macOS의 `accessibilityPerformPress`도 기존 터뜨리기 명령에 연결했다.
- 두 캐릭터의 과거 사용자 메시지에서 수신자 `persona`를 제외했다. assistant의 `persona`는 실제 화자로 유지한다. 같은 필드가 사용자 메시지에서는 수신자, 생성 응답에서는 화자를 뜻하던 모호성을 없앴다.
- 최신 질문, 캐릭터의 1인칭, 대사에 사용하는 이름과 JSON 내부 ID를 구분하도록 프롬프트를 정리했다. 입력 예산·기억 소유권·공개 단계·저장 구조·응답 후처리는 바꾸지 않았다.

같은 checkout에 있던 로그인 자동 실행과 병행 토이 통계 제거 작업은 별도 변경이다. 아래 모델 샘플은 두 작업의 기능 인수를 대신하지 않는다.

## 실제 모델의 전체 대화 경로

`src-tauri/src/app/model_quality_smoke.rs`는 합성 in-memory DB에서 검색, 검색 결과 재검증, `story::profile`, `story::prompt_history`, `with_user_context`, `conversation::generate_turn`을 거친다. 기존 GGUF를 읽기만 하며 사용자 DB나 모델을 변경하지 않는다. 기억 추출과 스토리 진행은 합성 fixture다. 실제 화면 표시나 1시간 업타임 시험이 아니다.

7개 사례는 단독 취향 정정, 두 명 취향 정정, 사용자와 화자 이름 구분, 민수→지연→새 민수의 동명이인 구분, 공개 단계 0·1·2다. 공개 전에는 합성 비밀과 비공개 assistant 기록을 프롬프트에서 제외하는 경계를 확인한다. 공개된 단계에서 모델이 실제 질문에 답하는지는 별도로 읽어 판정한다.

| 모델 | 수정 전 구조 결과 | 수정 후 구조 결과 | 수정 후 의미 판정 |
| --- | --- | --- | --- |
| Qwen3.5 4B Q4_K_M | 7/7 | 7/7 | 미달. UUID 발화와 비밀 질문 무시는 이 샘플에서 사라졌지만 사용자 취향을 자기 말로 혼동하는 답이 남음 |
| Qwen3.8 4B Q4_K_M | 6/7, 공개 2단계 화자 검증 오류 | 7/7 | 미달. 새 민수에게 이전 민수의 차 취향을 붙이고 두 화자가 거의 같은 문장을 반복함 |
| Qwen3.5 9B Q4_K_M | 이번 비교에서 실행하지 않음 | 7/7 | 미달. 나디르가 사용자 취향을 자기 것으로 말하고 새 민수에게 이전 민수의 차 취향을 적용함 |

수정 후 두 4B 모델은 공개 2단계의 합성 암호를 회상했다. 9B는 별꼬리만 암호를 답했고 나디르는 질문에 답하는 대신 기억에 기록돼 있다고 했다. 세 모델 모두 0·1단계의 비밀 제외와 기억 소유권·정정 출처 경계는 통과했지만, **구조 검사 통과는 모델 의미 품질 통과가 아니다.** 각 시퀀스를 한 번씩 실행한 관찰이며, 생성 결과와 시스템 부하가 달라 실행 시간을 성능 개선으로 비교하지 않는다. 모든 실행 뒤 앱이 만든 추론 프로세스의 종료를 확인했다.

잘못된 사용자 사실을 필터·저장 계층의 실패로 단정하지 않는다. 새 사용자 사례의 입력은 이전 사람의 기억을 `other_person`, `usableAsCurrentUserFact=false`로 제공했고, 모델이 그 구분을 따르지 않았다. 단어 포함 검사로 성공을 판정하거나 원문을 고쳐 성공처럼 보이게 만들지 않는다.

### 재현 방법과 출력

저장소 루트 `README.md`의 Rust·동봉 sidecar 환경에서 기존 GGUF의 절대 경로를 지정한다. 기본 테스트 실행에서는 모델 검사를 제외하며, 아래 명령은 실제 추론을 실행한다. 모델 검사는 하나씩 실행한다.

```sh
COMET_QA_MODEL=/absolute/path/model.gguf \
COMET_QA_OUTPUT_DIR=/tmp/comet-model-qa \
cargo test --locked --manifest-path src-tauri/Cargo.toml --lib \
  actual_model_app_path_semantics_smoke -- --ignored --nocapture --test-threads=1
```

출력 폴더의 실행별 UUID 아래 `app-path-samples.json`에 프롬프트·검색 결과·파싱된 원문·경계 판정·실행 오류·소유 runtime 종료 여부를 보존한다. production 경로가 잘못된 HTTP 원문을 노출하지 않는 경우에는 오류 문자열만 기록된다. 의미 품질은 `ungraded`로 저장하므로 응답 원문을 사람이 읽어야 한다.

`src-tauri/src/app/model_roster_smoke.rs`는 1–8명 순차 대화와 자동 독백·질문·두 명 대화를 별도로 기록한다. 첫 캐릭터에게만 대사 첫머리 지침과 상대를 스승으로 여기는 관계를 주어 지침 누출·관계 방향·문장 길이·반복을 확인한다.

```sh
COMET_QA_MODEL=/absolute/path/model.gguf \
COMET_QA_OUTPUT_DIR=/tmp/comet-model-qa \
COMET_QA_COUNTS=1..8 \
cargo test --locked --manifest-path src-tauri/Cargo.toml --lib \
  actual_model_roster_and_guidance_smoke -- --ignored --nocapture --test-threads=1
```

기본 대표 인원은 `1,2,3,8`이고 `1..8`은 전수를 실행한다. `roster-samples.ndjson`은 요청마다 저장하고 `roster-summary.json`에 최종 결과를 쓴다. 3명 이상에서는 `present_line`으로 이전 화자의 합성 기록을 만들고 다음 프롬프트에 같은 화자·원문이 들어가는지 확인한다. 실제 표시 영수증·재생 시간은 시험하지 않는다. 자동 대화도 production 프롬프트·생성 제한·파서까지만 사용하며 스케줄러·권한 gate·네이티브 재생은 별도 인수다.

### 인원수·지침·관계 관찰

Qwen3.5 4B의 최초 1–8명 전수와 자동 대화 3종에서 38개 실제 요청 중 37개를 파싱했다. 5명 대화의 마지막 응답은 JSON 오류로 실패했고 해당 검사는 종료 코드 101을 반환했다. 전체 39개 파싱된 대사의 길이는 Unicode 문자 기준 13–62자였다. 다음 화자에게 이전 화자의 ID·원문을 전달하는 경계는 모두 통과했다.

지침·관계 방향·반복은 미통과다. 첫 캐릭터만 사용해야 하는 `반짝!`이 상대의 대사에도 나타났고 두 사람이 같은 관계 문장을 말하거나, 한 화자가 `네, 네, 네, 네, 네!`를 답했다. 자동 독백도 사용자에게 질문했다. 최초 fixture의 이름 `하나`·`둘`은 숫자·복수 표현과 혼동될 수 있어 현재 fixture는 `다온`·`하린` 등 서로 다른 이름을 사용한다. 최초 결과는 이 한계를 포함한 관찰로 보존한다.

고유명으로 바꾼 뒤 2명·8명과 자동 대화 3종을 다시 실행했다. 12개 요청·14개 대사를 모두 파싱했고 이전 화자 전달 경계도 통과했다. 대사는 13–50자였다. 8명은 모두 자신의 이름을 말했고 자동 독백도 독백으로 답했다. 그러나 다온이 필수 `반짝!`을 빠뜨리거나 하린이 그 지침을 따라 쓰는 문제가 남았다. 다온에게 전달된 system prompt에는 지침 전문이 있어 이 사례는 입력 잘림이 아니다. 지정한 반말과 다른 존댓말, 관계 방향이 불명확한 답변도 남았다. 이 별도 단일 비교를 통계적인 품질 개선으로 일반화하지 않는다.

## 코드 검증

최종 통합 소스에서 Rust 라이브러리 513개 통과·5개 명시적 제외, 전체 target strict Clippy와 `git diff --check`가 통과했다. 제외된 실제 모델 smoke는 위 별도 실행 결과로 보고한다. 프런트엔드 TypeScript·Oxlint와 최종 Vitest 48개 파일·290개 테스트도 통과했다. 최종 Vitest는 컴파일·모델 실행이 끝난 뒤 작업자 1개로 실행했다. 앞선 작업자 2개 실행에서는 287개 통과·3개 시간 초과가 있었고, 해당 두 파일의 별도 재실행은 16개 모두 통과했다. 시간 제한을 늘리지 않았으며 최종 결과를 앞선 병렬 실행의 성공으로 바꾸지 않는다.

위키 TypeScript와 strict 정적 빌드를 통과했다. 빌드한 로컬 사이트에서 `공통 데스크톱 인수 기록` 검색 결과와 키보드 선택, 해당 문서 이동·검색어 강조를 확인했다.

## macOS 실제 실행

macOS 15.7.9(24G830), MacBookPro17,1, RAM 16 GiB, CPU 8개 환경에서 별도 `space.starlight.comet.common-qa` release 앱을 빌드했다. 초기 실행 파일 SHA-256은 `e0b9ca304e1168b5b5b8355692cd2bebe9a948c94be4005d80b7248d623ba0b5`이며 `codesign --verify --deep --strict`를 통과했다. 사용자 설치본은 교체하지 않았다.

별도 합성 사용자로 나디르·별꼬리 팩 가져오기와 활성 구성 변경, 음악·기기·캘린더·공·종이비행기·비눗방울 설치를 조작했다. 최종 활성 캐릭터는 나디르·텍스트 별꼬리 2명이다. Apple Music 빈 보관함에서 최초 조회 시간 초과가 한 번 있었고, 후속 조회는 `재생 대기 · Apple Music`과 `지금은 조용한 시간`으로 정상 회복됐다. 이를 실곡·아트워크·재생 제어의 통과로 확대하지 않는다.

기존 Qwen3.5 4B 파일의 절대 경로를 QA의 `직접 지정한 GGUF 파일` 설정에 저장했다. 이 선택은 모델 다운로드나 사용자 모델 파일의 변경을 만들지 않는다. QA SQLite 읽기 전용 무결성 조회는 `ok`였다.

네이티브 도구가 선택한 WebView 창만 노출해 별도 nonactivating 토이 패널의 시각·마우스·AXPress 동작과 메뉴 막대 트레이를 확인하지 못했다. 명령을 누른 것과 실제 물체의 색·크기·개수·터짐을 관찰한 것을 구분하며, 해당 항목은 남은 실기 인수다.

### 최종 빌드와 재시작

최종 release 실행 파일 SHA-256은 `b77eb63972215679f3f19ca041e8c9d20859d99ab300798d30ceeee0388b3b09`다. `codesign --verify --deep --strict`를 통과한 번들을 `/Applications/Comet Common QA.app`에 설치하고 실행했다. 빌드 전후의 소스 365개 파일 해시는 같았다.

초기 QA의 캐릭터 정의 3개·활성 구성 2명·사용자 1명·팩 2개와 설정이 그대로 유지됐고, 기존 메시지 47개는 ID·role·data와 순서가 완전히 같았다. 현재 빌드의 모두에게 입력에서 Qwen3.5 4B가 두 화자로 응답했다. 두 응답의 실제 `message_presentations` 영수증과 저장을 확인했으며, 별꼬리의 답은 `지난 대화` UI에서도 읽었다. 정상 종료·재시작 후 같은 질문·별꼬리 응답이 다시 표시되고 DB 무결성은 `ok`였다. 질문 1개·응답 2개가 추가돼 총 50개였으며 종료 시 소유 추론 프로세스도 남지 않았다.

이 실제 앱 샘플도 의미 품질은 미통과다. `내 이름은 공통검증자야. 나는 커피 대신 차를 좋아해. 내 이름과 좋아하는 음료를 말해줘.`에 나디르가 `네, 나디르야. 차도 좋아하지. 하지만 아직 내 이름과 좋아하는 음료를 말해줄 준비가 안 됐어.`라고 답했다. 별꼬리도 사용자 질문 대신 나디르에게 반응했다. 원문을 보존했으며 생성·표시·재시작의 성공과 구분한다.

최신 앱의 실행을 확인한 뒤 초기 Common QA 설치본과 실행 중이지 않은 이전 Toy Stats QA 번들만 휴지통으로 옮겼다. 최신 Common QA release 번들·설치본, 기존 사용자용 Comet 설치본, 모든 사용자 데이터·설정·팩·모델·빌드 캐시는 보존했다.

### 실행 시간·자원 관찰과 사용자 확인

초기 QA 프로세스는 14:50 KST에 실행했다. 15초 간격으로 05:51:33–06:46:35 UTC의 약 55분 동안 221개 표본을 수집했다. `ps`가 보고한 앱 본체 CPU는 평균 1.74%·중앙값 1.3%·표본 최고 18.1%였고, RSS는 23.4–113.5 MiB, 첫 표본 113.0 MiB·마지막 43.8 MiB였다. 이 구간에서 CPU의 지속 고부하나 RSS의 지속 증가를 관찰하지 않았다. 이는 별도 WebKit·LLM 자식 프로세스와 GPU 메모리를 합산한 수치가 아니며 최대 순간값·누수 부재를 증명하지 않는다.

같은 호스트에서 컴파일과 여러 모델 검사를 병행했다. 시스템 스왑 약 1.25 GiB도 확인했으나 Comet의 원인으로 귀속하지 않는다. 배터리 소모는 앱 단독 실측으로 판정할 수 없다. idle sleep 방지와 샘플 수집은 초기 프로세스 종료와 함께 끝냈다.

사용자가 선택지 출현을 직접 여러 번 확인했고 괜찮다고 알려, 추가 1시간 대기를 중단하고 최종 빌드 검증으로 진행했다. **선택지 출현은 사용자 확인 결과**이며 이 세션에서 시계를 앞당기거나 한 시간을 완주해 얻은 관찰이 아니다. 별도 QA의 스토리 답변은 0건이므로 이번 결과로 선택 결과·친밀도의 재시작 보존을 새로 검증했다고 하지 않는다.
